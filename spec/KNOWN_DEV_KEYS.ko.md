# 개발용 키 지문 목록 (`known_dev_keys.tsv`)

> This is the Korean edition. The canonical document is
> [`KNOWN_DEV_KEYS.md`](KNOWN_DEV_KEYS.md) (English).

PAIL 저장소에는 개발·시험용 키 재료가 커밋돼 있다. 그것을 그대로 실은 채 현장에
올라가는 것을 막는 것이 기동 게이트 `S8` 이고, 이 문서는 그 게이트가 읽는 목록의
포맷을 정한다.

## 1. 이 목록이 답하는 질문

`S8` 이 묻는 것은 **"이 키가 지금 저장소에 있는가"가 아니라 "이 키가 개발용으로
쓰인 적이 있는가"** 이다. 둘은 다른 질문이고, 답도 다르다.

개인키를 저장소에서 지워도 이미 배포된 사본은 회수되지 않는다. 그러므로 목록은
**단조**다 — 한 번 들어온 지문은 빠지지 않는다(§4). "트리에서 지웠으니 이제 안전
하다" 는 명제는 참이 아니고, 목록이 그것을 참으로 만들어 주어서도 안 된다.

목록에 실리는 것은 **공개키의 지문**뿐이다. 개인키도, 공개키 자체도 아니다.

## 2. 파일 문법

<!-- syntax: robot/pail_deploy_guard/known_dev_keys.tsv cols=3 fingerprint=^[0-9a-f]{64}$ kind=ed25519,spki -->

- 한 항목이 한 줄이고, 칸은 **TAB** 으로 나눈다. 정확히 세 칸이다.
- `#` 으로 시작하는 줄과 빈 줄은 항목이 아니다.
- 첫 칸은 **소문자 hex 64자**. 대문자·공백·축약은 항목이 아니라 오류다.
- 둘째 칸은 지문 이름공간(§3): `ed25519` 또는 `spki`.
- 셋째 칸은 라벨이다. 사람이 읽는 값이고, 판정에 쓰이지 않는다. 같은 키가 여러
  파일에 있으면 라벨이 ` | ` 로 합쳐진다.

파일 머리말이 열을 그대로 적고 있다:

<!-- pin: robot/pail_deploy_guard/known_dev_keys.tsv -->
```
# S8 공용 지문 목록 (PAIL-SD2-LLD-v1 §2). scripts/gen_known_dev_keys.py 가 생성한다.
# 손으로 고치지 말 것 — Go/C++ 상수와 이 파일을 대조하는 드리프트 테스트가 깨진다.
#
# 여기 적힌 것은 공개키의 지문이다. 개인키를 저장소에서 지워도(AS-16) 이미 배포된
# 사본이 남으므로 목록은 그대로 유지한다. 키를 옮기거나 이름을 바꿔도 지문은 같다.
#
# 열: fingerprint(sha256 hex)  kind(ed25519|spki)  label
```

이 파일은 손으로 고치는 것이 아니라 `spec/tools/gen_known_dev_keys.py` 가 생성한다.
게이트가 실제로 읽는 것은 이 파일이 아니라 **컴파일된 상수**이고(§7), TSV 는 그
상수의 원본이다. 파일에 의존하는 검사는 그 파일을 지우면 사라지기 때문이다.

## 3. 지문 이름공간

같은 키가 파일 형식에 따라 다르게 담긴다. 담긴 모양이 아니라 **키 자체**에 지문을
붙여야 파일을 옮기거나 인증서를 재발급해도 같은 값이 나온다.

<!-- pin: spec/tools/gen_known_dev_keys.py -->
```
지문 정의:
  ed25519  sha256(32바이트 공개키) hex
  spki     sha256(SubjectPublicKeyInfo DER) hex   — 인증서를 재발급해도 키를
           바꾸지 않으면 같은 값이므로, 인증서 파일 해시보다 키에 붙는다.
```

`ed25519` 는 keyring·키파일의 `ed25519_public_key_base64` 를 base64 로 푼 **원시
32바이트**에 붙는다. base64 문자열이나 JSON 바이트에 붙이지 않는다 — 같은 키를 다른
자에서 재면 두 값이 나오고, 그러면 목록이 같은 키를 두 번 세면서도 한 번은 놓친다.

`spki` 는 인증서에서 뽑은 **SubjectPublicKeyInfo DER** 에 붙는다. 인증서 파일의
해시가 아니다. 만료 갱신으로 인증서를 다시 발급해도 키를 바꾸지 않았다면 그것은
같은 키이고, 게이트는 같은 키를 계속 알아봐야 한다.

두 어휘 말고는 없다. 새 이름공간을 더하려면 생성기의 파서와 이 문서를 같이 고쳐야
하고, 검사 `K4` 가 둘이 갈라지는 것을 막는다.

## 4. 단조성

목록은 지문을 **잃지 않는다**. 생성기의 `--scan` 은 저장소에서 사라진 키의 행을
지우지 않고 라벨에 이력을 붙여 남긴다:

```
[저장소에서 제거됨 — 배포 사본 유효]
```

소실을 잡는 것은 사람이 아니라 `--check-monotone <기준TSV>` 다. 기준 대비 지문이
하나라도 빠지면 rc=1 이고, 그 뜻은 **"S8 이 더는 거부하지 못하는, 이미 배포된
개발키가 생겼다"** 이다.

목록을 줄이는 정당한 방법은 하나뿐이다 — 키를 회전하고, 폐기를 선언하고, 그 선언을
근거로 남긴다(§6). 행을 지우는 것은 회전이 아니다.

## 5. 무엇을 훑는가

생성기는 **git 이 추적하는 파일만** 훑는다. 목록은 커밋된 것의 함수여야지 작업 트리
상태의 함수여서는 안 된다 — 개발자가 로컬에서 만든 키는 커밋되지 않았으므로 배포
사본도 없고, 목록에 들어올 이유가 없다.

SROS2 enclave 의 `key.pem` 은 **범위 밖**이다. DDS 신원은 미들웨어가 적재하므로
검사 지점이 다르고, 여기서 함께 세면 두 검사가 하나로 합쳐진다.

훑을 자리가 이 트리에 하나도 없으면 생성기는 0건을 적어 내지 않고 **멈춘다**.
0건은 "개발키가 없다" 와 같은 바이트인데, 실제로는 훑지 않은 것이기 때문이다.
공개 스냅숏에서 도는 것은 `--check` 와 `--check-monotone` 뿐이다.

## 6. 잔여 허용 목록 (`known_dev_keys.allow`)

회전이 끝나기 전까지 어쩔 수 없이 남는 키를 적는 자리다. 열은 이렇다:

<!-- pin: robot/pail_deploy_guard/known_dev_keys.allow -->
```
# 열: fingerprint(sha256 hex 64자)  사유  폐기 선언 링크
# 지문 이름공간 = `sha256(파생된 32바이트 공개키)` — `known_dev_keys.tsv` 와 같다.
```

**항목은 지문 한 줄이다. 디렉터리·글롭·파일 경로는 항목이 될 수 없다.** 경로 단위
예외는 그 경로에 *나중에 들어오는 새 키까지 함께* 면제한다. 오늘 적은 예외가 내일
누가 그 디렉터리에 넣을 키에까지 미치는 것이다. 지문 단위는 그럴 수 없다.

세 칸이 모두 있어야 한다. 사유 없는 허용은 다음 사람이 지울 수 없고, 폐기 선언
링크 없는 허용은 "이 키가 왜 아직 살아 있는가" 에 답하지 못한다.

이 규칙을 집행하는 것은 파일의 글자가 아니라 **파서**다. 파일에 경로가 안 적혀 있다는
사실은 파서가 경로를 거부한다는 뜻이 아니다.

**오늘 항목은 0이다. 그것이 목표 상태다.**

## 7. 이 목록이 막는 것과 막지 않는 것

목록을 소비하는 기동 게이트는 하나다:

<!-- pin: TRUST_BOUNDARY.ko.md -->
```
| `S8` | 알려진 dev 키 또는 서명 없는 신뢰 앵커를 쓰고 있다 | 구현됨 |
```

`S8` 이 걸리면 프로세스는 **기동을 거부**한다. 계속 뜬 채 경고만 남기지 않는다.

`.allow` 파일 자체는 운용 중 키 철회를 집행하지 않습니다. 그 파일의 항목만으로
실행 중인 프로세스가 해당 키를 거부한다고 판단해서는 안 됩니다.

공개 기동 표는 별도로 개인키 파일의 접근 권한을 검사합니다.

<!-- pin: TRUST_BOUNDARY.ko.md -->
```
| `S19` | 이 프로세스가 여는 개인키를 소유자 밖의 계정이 읽을 수 있다 (`0600` 이 아니다) | 구현됨 |
```

파일 권한과 알려진 키 거부는 다른 통제입니다. 형식 선언이나 시험 자료가 추가 보호를
뜻하지 않습니다. 실제 공개 코드의 기동 규칙은 `TRUST_BOUNDARY.ko.md`를 확인합니다.

## 8. 이 문서가 어떻게 유지되는가

| 검사 | 무엇을 강제하는가 |
| --- | --- |
| `K1` | `pin` 이 딸린 인용 블록은 그 파일의 **바이트 부분문자열**이다 |
| `K2` | `pin` 이 가리키는 경로는 **공개 트리에 실린다** — 대조할 수 없는 인용은 주장이다 |
| `K3` | 실린 지문 목록의 전 행이 §2 가 선언한 문법에 맞는다 |
| `K4` | §3 의 어휘 == 생성기 파서의 어휘 == 목록에 실제로 나타나는 어휘 |

`K4` 가 세 값을 모두 재는 이유는 둘만 재면 어느 쌍이든 함께 틀릴 수 있어서다.
문서와 목록만 재면 파서가 모르는 어휘를 둘이 합의할 수 있고, 문서와 파서만 재면
목록이 조용히 낡는다.

검사기가 문서를 못 읽거나, 인용이 0건이거나, 목록이 0행이거나, 생성기에서 어휘를
읽지 못하면 rc=2 로 멈춘다 — "FAIL 0" 으로 내려앉지 않는다. **확인하지 못한 것과
확인했고 정상인 것은 다른 값이다.**

돌리는 법:

```
python3 spec/tools/spec_keys_check.py
```
