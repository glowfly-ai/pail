# 머클 적합성 벡터

`spec/merkle-vectors/` 는 트리 크기 0..9 의 RFC 6962 기지답(known-answer) 세트를
전수로 동결한다 — 루트 10 · 포함증명 45 · 일관성증명 36. 독립 구현이 살아 있는 로그에
붙기 **전에** 자기 머클 산술이 옳은지 알아낼 수 있게 하려는 것이다.

> 정본은 영문판 [`MERKLE_VECTORS.md`](MERKLE_VECTORS.md) 이다. 두 판이 어긋나면
> 영문판이 governs 한다.

## 1. 왜 전수 세트인가

`spec/proof-vectors/` ([`VERIFICATION_INPUTS.ko.md`](VERIFICATION_INPUTS.ko.md))
는 채집된 실선 바이트를 동결한다 — 실제 앵커 로그가 실제로 답한 것. 그것이 핀하는 것은
**형식**이고 **산술**이 아니다. 이유는 형식의 성질이 아니라 표본의 성질이다: 그 채집의
증명은 전부 트리 크기 1·2·4 에 산다. 전부 2의 거듭제곱이다.

작은 격차가 아니고, 짐작이 아니라 실측이다. 2026-08-30, 열여덟 벡터 상대로:

- RFC 6962 포함증명 검증기에서 **경계 접기 루프를 통째로 지워도** — 인덱스가 짝수인
  동안 계속 반으로 접는 그 `while` — 전건이 초록이었다.
- 일관성증명 검증기에서 **비-거듭제곱 씨앗 선택을 무너뜨려도** — 씨앗을 항상 옛 루트로
  잡고 첫 증명 해시를 쓰지 않게 해도 — 역시 전건이 초록이었다.

트리 크기가 2의 거듭제곱이면 두 가지 모두 도달 불가능하다. 제3자는 크기가 2의 거듭제곱이
**아닌** 모든 트리에서 틀리는 검증기를 만들어, 우리가 공개한 전부를 돌리고, 실패를 하나도
보지 않을 수 있다. 비-거듭제곱 크기를 한 번도 넘지 않은 로그라면 결함이 드러나지 않고,
넘은 로그라면 **한 번도 돈 적 없는 산술** 위에서 승인되거나 거부된다.

이 세트가 그것을 닫는다. 마지막 크기를 9로 잡은 것은 의도다 — 분할점 `k = 8` 이 잎
하나짜리 오른쪽 부분트리를 남기는데, 그것이 가장 자주 틀리는 모양이다. §8 이 동결
케이스 중 몇 건이 위 두 가지에 실제로 닿는지를 적고, 검사기가 그 수를 다시 잰다.

## 2. 해시 원시

도메인 분리 접두어 바이트 둘, 그리고 특수한 경우 하나.

<!-- vocab: hash -->

| 이름 | 접두어 | 핀 값 |
| --- | --- | --- |
| `leaf_hash` | `0x00` | `40b7deebc2f81803101885048466500bf310719859ee5b241885940f08dad99d` |
| `node_hash` | `0x01` | `645388217c67cbb482cba29ef06a913f7ad69cb8a12320174137514bea0cffed` |
| `empty_root` | `none` | `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` |

- `leaf_hash(d) = SHA-256(0x00 ‖ d)`. 핀 값은 §3 코퍼스의 잎 0 에 대한 `leaf_hash` 다.
- `node_hash(l, r) = SHA-256(0x01 ‖ l ‖ r)`. 핀 값은
  `node_hash(leaf_hash(잎 0), leaf_hash(잎 1))` 이고, 이는 크기 2 의 루트이기도 하다.
- `empty_root = SHA-256("")`. 빈 바이트열의 해시이고 접두어를 전혀 붙이지 않는다.
  크기 0 의 루트다.

접두어가 있어야 잎 해시와 내부 노드 해시가 서로 다른 공간에 산다. 접두어를 빠뜨린
구현은 **잎을 내부 노드로 제시할 수 있는** 트리를 만든다.

## 3. 잎 코퍼스

잎은 인쇄 가능한 규칙으로 생성한다. 받은 사람이 우리가 실어 보낸 바이트를 신뢰하지
않고도 이 문서만으로 모든 입력을 다시 만들 수 있게 하려는 것이다.

<!-- vocab: corpus -->

| 이름 | 값 |
| --- | --- |
| `leaf_prefix` | `pail-merkle-vector:` |
| `max_size` | `9` |

`0 <= i < max_size` 에 대해 잎 `i` 는 `leaf_prefix` 뒤에 `i` 의 십진 표기를 패딩 없이
붙인 ASCII 문자열이다 — 잎 0 은 `pail-merkle-vector:0`, 잎 8 은
`pail-merkle-vector:8`. 잎 데이터는 개행 없이 그대로 해시한다.

`leaves.json` 은 같은 데이터를 해시와 나란히 그대로 싣는다. 이 문단을 우리와 다르게
읽은 사람이 둘 중 어느 쪽이 틀렸는지 즉시 볼 수 있게 하기 위해서다.

## 4. 트리

앞의 `n` 개 잎에 대한 머클 트리 해시 `MTH(D[n])` 는 RFC 6962 §2.1 이다:

```
MTH({})     = empty_root
MTH({d0})   = leaf_hash(d0)
MTH(D[n])   = node_hash( MTH(D[0:k]), MTH(D[k:n]) )      n > 1
```

여기서 `k` 는 **`n` 보다 엄격히 작은 가장 큰 2의 거듭제곱**이다. `n = 8` 이면 `k = 4`,
`n = 9` 면 `k = 8`. 흔한 오류는 `n` **이하**의 가장 큰 거듭제곱을 쓰는 것인데, 그러면
모든 거듭제곱 크기에서 다른 트리가 나오고 나머지 모든 크기에서는 같은 트리가 나온다 —
그래서 거듭제곱만 담긴 세트는 통과하고, 오직 그것만 통과한다.

`roots.json` 은 0 부터 `max_size` 까지 모든 `n` 에 대한 `MTH(D[n])` 를 싣는다. 빠짐이
없는 이유는, 기지답 세트의 빠진 칸은 **아무도 확인하지 않은 크기**이고 그것은 통과한
크기와 같은 바이트로 읽히기 때문이다.

## 5. 포함증명

`inclusion.json` 은 `1 <= size <= max_size` · `0 <= index < size` 인 모든
`(size, index)` 쌍에 대해 한 건씩, 모두 마흔다섯 건을 싣는다. 각 건은 RFC 6962
`PATH(index, D[size])` 감사 경로다.

검증기는 `leaf_hash` · `index` · `size` · `proof` 를 받아 RFC 6962 순서로 접어 32바이트
값을 얻는다. 그 값이 **자기가 직접 계산한** 그 크기의 루트와 같을 때만 통과다 — `root`
칸과 같은지가 아니다. `root` 칸은 읽는 사람이 기대 답을 볼 수 있게 실려 있는 것이지,
검증기가 건네받은 수와 대조하라고 있는 것이 아니다. **루트를 유도하는 것은 루트를
검증하는 것이 아니다.**

<!-- sample: inclusion -->

```json
{
  "size": 3,
  "index": 2,
  "leaf_hash": "2a6a2cedd03e2d0037b2ab63727611cdbb58ab60aaee9685aa4b3de9179d75e3",
  "proof": [
    "645388217c67cbb482cba29ef06a913f7ad69cb8a12320174137514bea0cffed"
  ],
  "root": "6df12a6a277a1f96aa471f6568822d77ad0deec81f006f1da093c1399a038175"
}
```

§1 의 경계 접기 가지에 닿는 가장 작은 케이스다 — 잎 셋짜리 트리의 마지막 잎, 그 형제가
잎 둘짜리 부분트리인 경우.

`size = 1, index = 0` 케이스의 증명은 빈 목록이다. `[]` 로 직렬화되고 `null` 로는
절대 직렬화되지 않는다. "해시가 필요 없다" 와 "필드가 없다" 를 구분하지 못하는 구현은
짐작해야 하는데, 정답이 빈 증명인 경우가 바로 이 한 칸이다.

## 6. 일관성증명

`consistency.json` 은 `1 <= size1 < size2 <= max_size` 인 모든 `(size1, size2)` 쌍에
대해 한 건씩, 모두 서른여섯 건을 싣는다. 각 건은 RFC 6962
`SUBPROOF(size1, D[size2], true)` 다.

검증기는 `size1` · `size2` · `proof` · 옛 루트를 받아 두 값을 유도한다 — `size1` 의
루트와 `size2` 의 루트. **둘 다** 확인해야 한다. 두 번째만 확인하면 앞부분의 역사를
조용히 갈아치운 증명을 받아들이고, 첫 번째만 확인하면 어떤 미래든 받아들인다.

동결 케이스의 `root1` 도 `root2` 도 인증된 입력이 아니다. 실제 운용에서는 둘 다 서명된
체크포인트에서 온다(`VERIFICATION_INPUTS.ko.md` §2). 여기서는 기대 답이고, 검사기는
자기가 코퍼스에서 유도한 루트와 대조한다.

<!-- sample: consistency -->

```json
{
  "size1": 3,
  "size2": 5,
  "proof": [
    "2a6a2cedd03e2d0037b2ab63727611cdbb58ab60aaee9685aa4b3de9179d75e3",
    "809821060e34c816d7488f0c00f80109b0b43bd26b6deeba0d9734bc43305ccc",
    "645388217c67cbb482cba29ef06a913f7ad69cb8a12320174137514bea0cffed",
    "9333a5dd822b95cc8507a7d095c21b5f2df595e11ca8bb5c8eecc13e34bf81fe"
  ],
  "root1": "6df12a6a277a1f96aa471f6568822d77ad0deec81f006f1da093c1399a038175",
  "root2": "9e060c6832f2babb22ea7ad34e718e9fa90b217861d709badd96f6c1c73315b2"
}
```

`size1 = 3` 은 2의 거듭제곱이 아니므로 접기의 씨앗은 `proof[0]` 이고 남은 해시는
인덱스 1 부터 시작한다. §1 의 두 번째 가지다.

## 8. 이 세트가 실제로 닿는 곳

아무도 재지 않는 커버리지 주장은 시간이 지나면 거짓인 커버리지 주장이 된다. 아래 수는
전부 검사기가 동결 바이트에서 다시 유도한다 — 자기 검증기를 계측해 **어느 가지가
실제로 돌았는지**를 적는다.

<!-- vocab: coverage -->

| 이름 | 수 |
| --- | --- |
| `roots` | `10` |
| `inclusion_cases` | `45` |
| `consistency_cases` | `36` |
| `border_fold_cases` | `6` |
| `nonpow2_seed_cases` | `15` |
| `empty_proof_cases` | `1` |

- `border_fold_cases` — §1 의 경계 접기 루프가 한 번이라도 도는 포함증명 케이스.
  `spec/proof-vectors/` 에서는 이 수가 0 이다. 여기서는 6 이다 — 크기 3, 5, 6, 6, 7, 9.
- `nonpow2_seed_cases` — `size1` 이 2의 거듭제곱이 아니어서 씨앗을 옛 루트가 아니라
  `proof[0]` 에서 가져오는 일관성증명 케이스. `spec/proof-vectors/` 에서는 0 이다.
- `empty_proof_cases` — 증명이 빈 목록인 포함증명 케이스.

## 9. 매니페스트와 세트 해시

`spec/merkle-vectors/MANIFEST.sha256` 은 파일별 SHA-256 을 적고 이어서 세트 전체를
덮는 `set_sha256` 줄을 적는다. 세트 해시는 파일명 오름차순으로 늘어놓은
`"<hex>  <name>\n"` 줄들만을 입력으로 계산한다. 주석 줄과 `set_sha256` 줄 자신은
입력이 아니다.

<!-- vocab: claim -->

| 이름 | 값 |
| --- | --- |
| `merkle_set_sha256` | `b67f0bee29e86466f37a7b98cd345071a6db4b40a01eae50c897fe08e477aeb6` |
| `canon_set_sha256` | `bbddff16fb5997faeff47bf6913e64d9675178d2ddffd5828aa898a235688701` |

매니페스트가 둘이고 세트가 둘인 것은 의도다. `canon_set_sha256` 은
`spec/vectors/canon/` 을 덮는다 — 바이트를 어떻게 적는가 — 그리고 그것이
[`CONFORMANCE.ko.md`](CONFORMANCE.ko.md) 의 적합성 주장이 지목하는 세트 해시다.
`merkle_set_sha256` 은 이 세트를 덮는다 — 그 바이트 위의 로그 산술. 둘은 서로 무관한
이유로 바뀐다. 한 매니페스트로 합치면 한쪽을 개정하는 것이 다른 쪽에 대해 공표된 모든
적합성 주장을 무효로 만든다.

그 귀결은 읽는 사람이 알아서 발견하게 두지 않고 그대로 적는다: **`CONFORMANCE.md` 의
적합성 주장은 직렬화 평면만 덮는다.** 이 머클 세트를 통과하는 것은 오늘 그 주장의
일부가 아니다. 따라서 어떤 구현은 §5 와 §6 을 틀린 채로 호환 표기의 자격을 가질 수
있다. 이것이 바뀐다면 바뀌는 자리는 `CONFORMANCE.md` 와 그것을 재는 검사기이지 이
문단이 아니다.

## 10. 세트 쓰는 법

시험 대상 구현에 대해:

1. §3 으로 코퍼스를 다시 만든다. `leaves.json` 의 `leaf_hash` 를 각각 대조한다. 여기서
   어긋나면 §2 의 접두어 바이트가 틀린 것이고 그 뒤의 무엇도 의미가 없다.
2. `roots.json` 의 모든 `n` 에 대해 `MTH(D[n])` 를 계산한다. 비-거듭제곱 크기에서만
   어긋나면 §4 의 `k` 규칙이 틀린 것이다.
3. `inclusion.json` 의 각 건을 2 단계에서 **자기가** 계산한 루트에 대해 검증한다. §8 의
   여섯 건에서만 실패하면 경계 접기 가지가 틀렸거나 없는 것이다.
4. `consistency.json` 의 각 건에서 두 루트를 모두 유도해 2 단계와 대조한다. §8 의
   열다섯 건에서만 실패하면 씨앗 선택이 틀린 것이다.

`spec/proof-vectors/` 는 통과하면서 3 이나 4 단계에서 실패하는 것이, 이 세트가 드러내려고
만들어진 결함의 예상 서명이다.

## 11. 실려 나가는 검사기가 볼 수 없는 것

`spec/tools/spec_merkle_vectors_check.py` 는 동결 바이트와 이 문서를 상대로 돈다.
아흔한 개의 답을 전부 RFC 6962 정의에서 새로 쓴 구현으로 다시 유도하는데, 그 구현은
답을 만들어 낸 쪽과 독립이다. 그것이 하중을 지는 부분이고, 그것은 실려 나간다.

세트를 생성한 프로그램은 내부에 있고 실려 나가지 않는다. 검사기가 이 리포 안에서 돌
때는 §3 의 `leaf_prefix` 와 `max_size` 를 그 프로그램의 소스에도 핀하고, 공개
스냅숏에서는 그 칸을 조용히 통과시키는 대신 **건너뛰었다고 인쇄한다.** 조용히 없는
검사는 통과한 검사와 구분되지 않는다.

경계 하나를 더 적는다. 여기서 읽는 편이 나중에 다시 발견하는 것보다 쉽기 때문이다:
`spec/tools/spec_verification_inputs_check.py` 는 자기 RFC 6962 구현을 따로 품고 있고,
그것이 겨누는 벡터는 §1 의 거듭제곱 전용 채집이다. 그쪽 산술을 떠받치는 것은 그
채집이 아니라 이 세트에서 뽑은 기지답 값이다.
