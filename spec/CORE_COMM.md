# Basic communication contract — implementation candidate

Status: one communication contract, and no setting selects it. Existing signed bundles are unchanged.

## Scope

PAIL authorizes or blocks actions and records Evidence. It does not replace a fleet manager, plan execution protocol, navigation controller, or motor bus. This change adds no network hop or synchronous acknowledgment to each motor command. It does not measure motor response or guarantee a control-loop deadline.

Existing gRPC/Protobuf, mTLS, ROS 2/DDS/SROS2 and robot-specific drivers remain in place. No custom STX/ETX framing or new transport is introduced.

## Compatibility and activation

There is one communication contract and no setting that selects it. `PAIL_CORE_COMM_CONTRACT` — which once chose `legacy` (the C0 wire) or `v1` — has no meaning: the variable being set at all — any value, an empty one (`PAIL_CORE_COMM_CONTRACT=`) included — refuses startup with `CORE_COMM_CONTRACT_SETTING_REMOVED: PAIL_CORE_COMM_CONTRACT has no meaning (there is one communication contract); unset it`, never a silent interpretation; only an absent variable starts. Every implementation tests presence (Go `os.LookupEnv`, C++ `getenv() != nullptr`, Python `in os.environ`, Rust `env::var_os`, shell `${VAR+x}`). That message is the same bytes in every implementation (Go `internal/corecomm`, the ROS 2 gate `core_contract.hpp`, the Python examples `core_operation_wire.py`, the Microduck adapter, the hardware scripts); this file is its source. The wire keeps its version numbers — operation and report receipts carry `contract_version = 1`, the census answer carries `pail-core-comm-contract: v1`, the agent's readiness probe reports `core_comm_contract = v1` — as protocol versions, not as a mode. The Issuer, gateway and report producers must be built from the same schemas. A C1 report without a valid C1 receipt is unconfirmed; there is no fallback to fabricated confirmation. A nil answer or a transport error is retried; a successful RPC that answers `accepted=false` is the Issuer's definitive refusal and is retained by the robot agent as rejected evidence, never confirmed and never retried, so it cannot hold later reports behind it.

**Receive-only compatibility.** The Issuer still accepts a C0 decision report (`receipt_contract_version = 0`) and a plan-status query without an operation id from an older robot agent: such reports are journaled unattributed and carry no C1 assurance. Nothing selects this path — it is the request's own shape — and it is not a second contract. A request the contract cannot canonicalise (a non-finite number, a value outside an enum, `:` in an identifier) is refused at the wire (`InvalidArgument`) before any journal record; an operation the journal cannot persist is refused with `Unavailable` and issues nothing.

The TB3 and Microduck manifests and launchers carry no contract setting, print no `CONTRACT=` line and have no `--contract` option. A run recorded by an earlier release under the removed `legacy` contract is not revived — lifecycle commands answer `LEGACY_RUN_UNSUPPORTED`; clean it with this release's `cleanup --state <dir>` (stopping it with the release that created it also works), then start a new run. HA is unsupported (below).

Version guard (preview.36 hardware evaluation P36-M1; recovery model preview.38, P37-M1/L1/N1): the Issuer answers every `ReportGatewayCensus` with the response header `pail-core-comm-contract: v1` — the protocol version token, kept byte-for-byte so that preview.36–39 robot agents accept this Issuer (an Issuer older than the handshake sends none; two or contradictory values are not a `v1` answer). The robot agent refuses to start when its first census does not answer `v1` (`PAIL STARTUP REFUSED: CORE_COMM_COHORT_MISMATCH`, exit 78). A mismatch while running, or a `FailedPrecondition` refusal of a C1 report, is a *cohort hold*: new authority is withheld (`GetActiveToken` answers `CORE_COMM_COHORT_MISMATCH`), the readiness probe reports `report_storage_state=COHORT_MISMATCH`, a warning with the held report counts repeats every 30 s from a timer (it does not depend on another Issuer call failing), and the agent re-declares the census with a 5 s → 60 s backoff. The hold clears on the next *verified* census answer that carries `v1` — an answer with a verdict, an epoch not below the one already seen, from the current connection and generation; a late answer of an earlier connection or a lower epoch changes nothing — and the agent logs `CORE_COMM_COHORT_RESTORED … other holds: …`. Only the cohort hold clears: the critical storage fault (`CORE_REPORT_STORAGE_UNHEALTHY`, which stands until restart), the execution fence and every other reason to withhold authority keep their own rules, and the restore line names the ones still in force. C1 reports are never downgraded to the C0 wire and never dropped; they wait in the durable queue and the critical outbox and are delivered when the cohort matches again. Downgrading a running Issuer below the v1 handshake is not supported: a plan submitted between the downgrade and the agent's next census or report can be answered by the old Issuer. On the ROS 2 gate, a `PAIL_CORE_COMM_CONTRACT` variable present at all (any value, an empty one included) refuses node construction (`CORE_COMM_CONTRACT_SETTING_REMOVED`); the real gRPC token provider always reports decisions in the C1 receipt form, and the static and no-token providers never send a report (test providers). (Until 0.2.0-preview.39 a `v1` selection was refused on a non-gRPC provider — `CORE_COMM_CONTRACT_REQUIRES_GRPC`; with no selection there is nothing to refuse: a non-reporting provider is simply not a reporting one.)

Everything that speaks this protocol — producers, proxies, seams, generated stubs, command-line tools, journal readers and deployment configuration — is listed in `spec/CORE_COMM_CONSUMERS.tsv` with how it handles the C1 fields and where that is tested; the inventory is checked against every call site in the tree. The PVS seams relay the upstream Issuer's status and its `pail-*` metadata unchanged and never answer an acceptance the Issuer did not give. The PVS Python stubs are generated from these protos with a pinned toolchain and bundled (`pvs-public/runner/gen_grpc_stubs.md`).

The first C1 implementation supports a single Issuer journal owner. `PAIL_HA_MODE=sync` or a standby role refuses startup (`CORE_COMM_V1_HA_NOT_VALIDATED`): replicated receipt recovery/promotion has not been validated and HA is **unsupported** in this release line — with the removal of the `legacy` contract there is no HA configuration left to select. Never roll back a journal containing new records into an older reader without a reviewed migration.

## E — report ownership and effect

ReportDecision adds `report_id`, `report_digest`, `receipt_contract_version` and optional gateway attribution. Immutable report fields are hashed independently of transport delivery fields. The first persisted gateway attribution is retained across retries; the producer's original chain and digest are not rewritten.

A receipt binds event ID, digest, robot, contract and receiver instance. It separates:

| Dimension | Meaning |
|---|---|
| LOCAL_BUFFERED | Volatile local queue; not disk persistence |
| LOCAL_DURABLE | Gateway has taken disk-backed ownership |
| ISSUER_DURABLE | Issuer journal record has been durably acknowledged |
| PENDING / UNKNOWN | Requested authority effect not established |
| APPLIED + LOCAL_LEASE | Existing local delegated authority bookkeeping only |
| APPLIED + ISSUER_CHAIN | Issuer-side effect confirmed |
| ISSUER_DURABLE + NOT_APPLICABLE + NEW | Recorded in the Issuer journal, no authority effect — including an observation no chain owned (`chain_attributed=false` in the record) |
| TERMINAL_REJECTED | Negative/unknown effect retained; not success — only for a report that claimed an effect and was refused |

Fatal confirmation requires a matching ISSUER_DURABLE/APPLIED/ISSUER_CHAIN receipt. Local persistence alone does not release a latch. A durably rejected event is quarantined so it cannot block unrelated later reports; no effect-confirmed callback is made. The quarantine is bounded (4096 entries, 16 MiB; `spec/DURABLE_STORES.tsv`): beyond the bound a refused observation is counted and not retained, and a refused effect report raises the critical fault. A step-completion report for a step whose motion was never permitted (only refused commands, for example `ERR_CONSTRAINT`) is refused by the Issuer as `COMPLETION_NOT_ACCEPTED`; under C1 its receipt is `REJECTED / TERMINAL_REJECTED` and the agent quarantines it. That is the intended outcome, not a defect (preview.36 evaluation P36-N2).

C1 critical reports use a separate disk outbox under `PAIL_REPORT_QUEUE_DIR/core-comm-critical`. It has a single-process ownership lock, fsync and atomic rename, and preserves report identity on replay. Defaults: 4096 retained pending/rejected entries, 16 MiB. Corrupt or full storage is an explicit fault, not memory fallback. C1 refuses a memory-only report queue. Producer memory before the first durable gateway receipt is **not** claimed to survive power loss. The interposer/Microduck producer stops reporting healthy if it loses a critical report to queue overflow; an unrelated successful report does not clear that fault.

In the journal mirror and the export vocabulary the two record kinds are named `CORE_OPERATION` (100) and `CORE_REPORT` (101); rows an older mirror indexed as `TYPE_100`/`TYPE_101` take these names on re-index. Anchor and the external verifiers check the opaque record hash and the chain, not the receipt semantics.

Ordinary observations retain event IDs in the existing decision journal but do not consume permanent per-operation tombstones. They may be repeated. `core_comm_record_confirmation=true` denotes the durable receipt record, not another authorization event.

## I — authorization request receipts

Existing SubmitActionPlan, CancelPlan and GetPlanStatus carry optional operation fields. No new authorization RPC is introduced.

A key is scoped by authenticated requester, robot, operation kind and operation ID. Missing operation ID in a C1 submit/cancel uses its existing plan ID. The same key and payload returns the stored outcome; different content conflicts before a new effect. A different operation ID cannot reuse the same plan identity to mint another chain. Status lookup repeats authorization checks.

Successful submit retries return the original chain and historical receipt, **not a refreshed token list**. Current authority status is separate. Cancelled, expired, consumed or superseded authority is not revived by retrieving a receipt. A resubmitted SubmitActionPlan therefore answers with the *stored* outcome: `status` is the original result (`ACCEPTED` even after a cancel), `tokens` is empty, and `receipt.current_authority_state` names the authority now (`CANCELLED` after a cancel). A client decides liveness from the receipt and from `tokens`, never from `status` alone (preview.35 evaluation P35-N1). `current_authority_state` names the authority of the receipt's own chain: `ACTIVE`, `CANCELLED`, `SUPERSEDED` (the robot's current chain is a different one), `UNKNOWN` (no chain known for the robot) or the store's other state names; a rejected operation created no chain, so its receipt says `NONE` (0.2.0-preview.41, preview.40 evaluation P40-N1).

The authenticated blackbox journal uses records 100 (operation) and 101 (critical report). A prepared operation without a durable terminal outcome is UNKNOWN after restart, and new authority is held for that robot. The implementation does not guess that a timed-out request did not execute. Existing CancelPlan may resolve the hold only after a durable authenticated withdrawal; historical outcome remains unknown. A cancellation is never reversed because receipt storage failed. The journal's segments rotate (64 MiB or 24 h) and the Issuer never deletes one: retention, archival and disk monitoring are the operator's responsibility (`spec/DURABLE_STORES.tsv`, blackbox row; owner decision 2026-10-29) — a full disk stops issuance, never the ledger's integrity.

The index retains full receipts, currently up to 4096 entries / a 64 MiB admission budget. New work is refused before the reservation is exhausted; committed receipts and unknown outcomes are not evicted. `EXPIRED_RECEIPT` is reserved for a later reviewed compaction mechanism; this implementation does not delete receipts or reuse their identities.

## R — read-only readiness

`examples/common/core_readiness.py` checks the existing local status interfaces. It verifies nonce, OS peer credentials, executable hash, boot/process/config generation, expected named DDS endpoints and QoS compatibility, and fresh required evidence/safety inputs. A second sample detects a changed generation. Gateway and driver identity are checked separately. A ready result says `IO_TOPOLOGY_AND_REQUIRED_INPUTS`; physical execution remains `NOT_OBSERVED`. It neither sends a movement command nor grants authority. DDS graph presence is not a physical-delivery or braking test. The operator declaration it reads (`--manifest`) is documented field by field in `examples/common/core_readiness.manifest.example.json`; every value is taken from the running rig and reviewed — the example is a template, not an observed file (preview.35 evaluation P35-L3).

Restarting the robot side is a manual operation of the hardware rig (`start_demo_rig.sh restart-gate`, driven by the console's "restart robot side"): the gate container is started again as `up` did and the command ends with `GATE_RESTARTED` once IO readiness is observed. It keeps no operation record; the readiness check above is the way to confirm the restarted gate.

## Acceptance boundaries

Unit, concurrency, journal-recovery, real gRPC and Linux UDS tests are implementation evidence, not hardware acceptance. Before enabling C1 as a supported release cohort, run the mixed-version rollout, storage-fault scenarios and command-path latency/jitter measurements. The previously reported intermittent hardware DDS restart issue remains open until directly reproduced and verified.

Network-loss testing must separately report availability, forbidden-authority effects, Evidence ownership and unachieved prerequisites. A 30% packet-loss scenario is not automatically a requirement for uninterrupted motion, and a scene that never began is not evidence of stop performance.
